核心结论（One-Liner）
Function Calling 与 MCP 不是互相替代的关系，而是互补的关系。它们作用在大模型调用链路的不同环节：Function Calling 作用在「模型/模型 API ↔ 中间人」之间，MCP 作用在「中间人 ↔ 外部函数」之间。两者可以在同一个链路中同时存在。

1. 为什么做这期视频：常见误区

自 Anthropic 推出 MCP 之后，网络上最流行的一种说法是：

流传最广的错误说法
「MCP 统一了 Function Calling 的协议，有了 MCP 之后，Function Calling 就没有存在的必要了。」

看上去很合理 —— 「两者都是调用工具，MCP 更标准，所以替代 Function Calling」。但 UP 主认为：这种类比是错的。两者作用的链路环节根本不同，未来很长时间都将同时存在、各自发挥价值。

2. 什么是 Function Calling

2.1 起点：模型的知识有边界

模型训练完成后，知识库就「定格」了。超出训练截止时间或私有领域的问题，模型要么回答「不知道」，要么「胡言乱语」（幻觉）。比如问：「纽约明天的天气怎么样？」—— 模型自己无法回答。

2.2 定义

Function Calling 的定义
Function Calling 是模型与外部工具交互的一种能力。具体说：模型能从候选工具列表中挑选要调的工具、给出调用参数、并能解析工具的执行结果来给出最终答案。

注：「工具」这种说法比较抽象，本质上就是编程语言里的函数。比如查天气可能对应 get_forecast(lat, lng) 函数。所以 "Function Calling = 函数调用 = 使用工具"。

2.3 模型自己不能真的调函数

注意一个常被忽略的点：

关键认知
模型本身没有执行能力。它只能「输出一段表示想调用某工具」的文本结构，真正去调用函数的是中间人（比如 OpenAI 服务器、或你自己写的应用后端）。

3. 完整链路分析：ChatGPT 查天气的故事

以「纽约明天的天气怎么样」这个问题为例，假设 ChatGPT 内部用 Function Calling 实现搜索（实际未必，仅为讲解链路），整个链路涉及四个角色：

图 1：以 ChatGPT 查天气为例的端到端上下游交互链路

3.1 整链路十步

①
用户向 ChatGPT 应用发问：「纽约明天的天气怎么样」。
②
ChatGPT 应用把用户问题 + 可用工具列表（如 search）一起发送给 OpenAI 服务器 → GPT-4o 模型 API。
③④
模型评估：「自己不知道，需要 search 工具」，返回一个 tool_calls（包含工具名 + 参数），而不是真的去执行。
⑤⑥
OpenAI 服务器（中间人）拿到 tool_calls，真正去调用网络搜索函数，拿到结果。
⑦⑧
中间人把工具结果再次喂给模型，模型基于结果做自然语言总结，返回最终答案。
⑨⑩
OpenAI 服务器把最终答案返回给 ChatGPT 应用 → 展示给用户。

4. Function Calling 到底作用在哪一段？

很多人的第一直觉是：「Function Calling 翻译过来就是函数调用，那它一定发生在第 ⑤ 步『真的去调函数』那里」—— 这是最常见的错误。

名字的误导性
Function Calling 名字虽然带「Calling」，但它并没有规定函数到底如何被调用。它规定的是：模型如何接收工具列表描述、如何返回想调用哪个工具及参数、如何接收工具的执行结果。

4.1 进一步拆分模型层

「GPT-4o 模型」这个表述并不准确。OpenAI 服务器调用的不是模型本身，而是模型 API（HTTP 接口）。API 内部还做一次「参数格式 → 模型可接受的输入」的转换。所以严格来说：

  • 狭义：Function Calling 作用在「模型 API ↔ 真实模型」之间。
  • 广义（常用）：作用在「中间人（应用后端）↔ 模型 API」之间 —— 这是开发者真正打交道的层级。
图 2：Function Calling 的真正作用环节（不在「中间人 ↔ 函数」这一段）

4.2 一句话判定：模型是否具备 Function Calling 能力

判定标准
如果一个模型 / 模型 API 能做到下面三件事，就具备 Function Calling 能力：
  1. 能解析请求参数中的工具列表（tools）字段；
  2. 能从中挑选出要调用的工具名称及参数；
  3. 能解析工具的执行结果并生成最终答案。

5. Function Calling 协议细节

UP 主写了一个最小演示应用 MarkChat，把模型 API 的请求/返回都打到日志里，便于观察协议字段。

5.1 第一次请求模型 API（带工具列表）

{
  "model": "gpt-4o",
  "stream": false,
  "messages": [
    { "role": "user", "content": "纽约明天的天气怎么样" }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "search",
        "description": "在网络上搜索内容",
        "parameters": {
          "type": "object",
          "properties": {
            "query": { "type": "string", "description": "需要搜索的内容" }
          },
          "required": ["query"]
        }
      }
    }
  ]
}
  • model：使用的模型名。
  • messages：历史消息列表（首次请求里只有用户问题）。
  • tools：候选工具列表，每个工具的入参用 JSON Schema 描述。
  • stream：是否流式返回，演示场景设为 false 便于观察。
关于 JSON Schema
JSON Schema 是「对另一段 JSON 结构的描述」。上面的 schema 表示：参数必须是对象，必须包含一个字符串字段 query。下列两段 JSON 都满足该 schema： 
{ "query": "weather in NY tomorrow" }
{ "query": "纽约明天天气" }

5.2 模型 API 第一次返回（tool_calls）

{
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "call_abc123",
            "type": "function",
            "function": {
              "name": "search",
              "arguments": "{\"query\":\"纽约明天的天气\"}"
            }
          }
        ]
      }
    }
  ]
}

关键是 tool_calls：模型表达「我想调 search 工具，参数是这个」。模型本身不执行，由 MarkChat（中间人）去执行。

5.3 第二次请求模型 API（带工具执行结果）

{
  "model": "gpt-4o",
  "messages": [
    { "role": "user", "content": "纽约明天的天气怎么样" },
    {
      "role": "assistant",
      "tool_calls": [ { "id": "call_abc123", "type": "function",
                        "function": { "name": "search",
                                      "arguments": "{\"query\":\"纽约明天的天气\"}" } } ]
    },
    {
      "role": "tool",
      "tool_call_id": "call_abc123",
      "content": "纽约明天晴，气温 18~26℃，微风。"
    }
  ],
  "tools": [ /* 同上 */ ]
}

5.4 模型 API 第二次返回（最终答案）

{
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "纽约明天天气晴朗，气温大约在 18~26℃，会有微风，整体很舒适。"
      }
    }
  ]
}

6. 案例代码：MarkChat 的五步法

核心函数是 process_user_query()，逻辑可以浓缩为 5 步：

1
调用模型 API（首次） —— 把 self.history + tools 一起发给模型。
2
提取工具名称和参数 —— 从 tool_calls 中解析。
3
真正调用工具 —— 由本地的 self.execute_tool() 完成（HTTP / SDK / 子进程都行）。
4
再次调用模型 API —— 把工具结果塞进 messages，让模型基于结果生成回答。
5
返回最终答案 —— 抽取 content 字段，附加进历史，输出给用户。
# 简化版伪代码（MarkChat/backend.py 的核心思路）
def process_user_query(self, query: str):
    self.history.append({"role": "user", "content": query})

    # ① 首次调用模型 API
    first_resp = self.call_model(self.history, tools=self.tools)
    message = first_resp["choices"][0]["message"]
    self.history.append(message)

    if "tool_calls" in message and message["tool_calls"]:
        # ② 提取工具调用
        call = message["tool_calls"][0]
        tool_name  = call["function"]["name"]
        tool_args  = json.loads(call["function"]["arguments"])

        # ③ 真正执行工具
        tool_result = self.execute_tool(tool_name, tool_args)
        self.history.append({
            "role": "tool",
            "tool_call_id": call["id"],
            "content": tool_result
        })

        # ④ 第二次调用模型 API（带工具结果）
        second_resp = self.call_model_after_tool_execution(self.history, tools=self.tools)
        final_message = second_resp["choices"][0]["message"]
        self.history.append(final_message)

        # ⑤ 返回最终答案
        return final_message["content"]
    else:
        return message["content"]
为什么要维护 self.history？
模型本身没有记忆。要让它「知道之前发生了什么」（比如知道刚刚选了什么工具、工具返回了什么），必须把这些信息显式塞回 messages 一起发回去。

7. MCP 与 Function Calling 在链路中的位置

回到链路图。MCP 是「函数的发现与调用协议」，它规定的是：

  • 中间人（client）如何发现外部有哪些函数；
  • 中间人如何调用这些函数；
  • 函数提供方（server）如何声明自己提供的能力。

所以 MCP 完全作用在「中间人 ↔ 外部函数」这一段，跟模型没有直接关系。

图 3：Function Calling 与 MCP 在同一条链路中分工示意

对比一览表

维度Function CallingMCP
所处环节模型/模型 API ↔ 中间人中间人 ↔ 外部函数（工具提供方）
解决的核心问题让模型「会选工具、能解析结果」让工具「能被标准化地发现与调用」
谁负责实现大模型厂商（OpenAI、Anthropic 等）工具的提供方（MCP Server）+ 调用方（MCP Client）
是否规定工具实现细节否（不管你怎么实现 search）是（规定 server / client / 协议）
是否互相替代❌ 否 —— 互补，可同链路共存

8. 同链路同时使用 Function Calling + MCP

UP 主在 MarkChat 中演示了同时使用两种技术的改造方式：只需要替换 execute_tool 函数。原来的 execute_tool 返回的是写死的假数据，改用 execute_tool_with_mcp 后，内部会：

  1. 启动一个 MCP Client；
  2. 连接项目中事先准备好的 MCP Server；
  3. 通过 MCP 协议调用 Server 暴露的工具；
  4. 把结果返回给上层。
# 改造点：只换工具执行这一步，前后流程完全不动
- tool_result = self.execute_tool(tool_name, tool_args)
+ tool_result = self.execute_tool_with_mcp(tool_name, tool_args)
图 4：MarkChat 中 Function Calling + MCP 共存的上下游交互
结论性观察
改造后：
  • 模型那一段仍然走 Function Calling 协议（接收 tools、返回 tool_calls）。
  • 工具执行那一段切换为 MCP 协议（client 连 server）。
  • 两套协议彼此独立、各管一段、互不干扰。

9. 总结与判定标准

9.1 一图记忆

Function CallingMCP
定位模型「会用工具」的能力工具「被标准化调用」的协议
规定什么tools 字段格式、tool_calls 返回格式、工具结果回传格式工具发现、工具调用、传输方式（stdio / SSE / HTTP）
不规定什么工具内部如何实现模型如何挑选工具
实现者大模型厂商任意工具提供方

9.2 Function Calling 的最终判定

当一个模型 / 模型 API能够：
  1. 解析请求中的 tools 字段；
  2. 从中挑选出要调用的工具名 + 参数；
  3. 解析工具的执行结果并据此回答；
就称它具备 Function Calling 能力。

9.3 实战 Checklist

  • ✅ 设计链路时先想清楚：哪一段是「让模型选工具」，哪一段是「真的去执行工具」。
  • ✅ 「让模型选工具」 → 用 Function Calling 协议（tools + tool_calls）。
  • ✅ 「真的去执行工具」 → 内部直接写函数 / 调 HTTP / 调 SDK / 或用 MCP 协议。
  • ✅ 维护好 messages / history，模型没有记忆，必须靠你回喂。
  • ✅ 把模型 API 的输入输出落盘成日志，是搞懂协议的最有效手段。
