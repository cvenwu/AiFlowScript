先抓住 5 个关键概念

Context Window模型一次输入可容纳的上下文窗口。它有长度上限，也有注意力有效性问题。
Sliding Window窗口满了就丢旧留新。简单，但会误删长期重要信息。
RAG Memory把历史消息当文档，切 chunk 入库，再按 query 检索召回。
Distilled Markdown把旧对话提纯为结构化长期记忆，落到 Markdown 文件中。
Key Strategy决定记忆如何归类与合并：预定义更稳，动态生成更灵活。

00:00 - 01:48

一、为什么 LLM 原生没有记忆？

讲解要点

  • LLM 可被理解为一个输入到输出的函数：训练结束后参数固定，用户输入不会改变模型参数。
  • 产品里看起来“有记忆”的大模型，通常是在 Agent 层把历史上下文重新注入输入。
  • Memory 的第一层本质不是模型真的记住了，而是把相关历史打包进 Context Window。
思路解析：这一章先拆掉一个常见误解：记忆不是 LLM 的原生能力，而是系统工程能力。理解这一点，后面所有“存什么、取什么、何时加载、怎么压缩”的问题才会成立。

01:48 - 03:39

二、Context Window 为什么会成为瓶颈？

讲解要点

  • 把所有历史都拼进输入，会让上下文越来越长。
  • 长上下文带来两类成本：存储/计算负载，以及注意力扩散。
  • 注意力扩散会让模型无法把注意力放到正确内容上，最终表现为幻觉、答非所问或遗漏关键约束。
思路解析：长上下文能力是必要条件，不是充分条件。即使模型标称支持百万 token，工程上仍要考虑延迟、费用、召回准确性和模型是否真的能利用远距离信息。

03:39 - 05:10

三、滑动窗口：简单但粗糙的补丁

讲解要点

  • 滑动窗口的策略是“丢旧留新”：当窗口满了，移除最早内容，加入最新内容。
  • 它的隐含假设是：越新的内容越重要，越旧的内容越不重要。
  • 这个假设在 Agent 中经常失效：用户偏好、项目背景、长期约束往往最早出现，但后续一直重要。
思路解析：滑动窗口解决了容量问题，却没有解决“重要性判断”问题。Agent Memory 的核心价值正是把“时间近远”替换为“语义相关性与长期价值”。

05:10 - 07:55

四、两大路线：数据库/RAG 与 Markdown/蒸馏

讲解要点

  • 数据库/RAG 路线：把历史消息当作文档，切 chunk、加元信息、入库、检索。
  • Markdown/蒸馏路线：把即将被滑出窗口的内容提纯为结构化记忆，写入可读文件。
  • 两者分别偏向“检索召回”和“结构沉淀”，不应简单判断谁绝对更先进。
思路解析：视频的主线从这里进入工程落地：同样是记忆，数据库方案更像信息检索系统，Markdown 方案更像长期维护的知识档案。

07:55 - 10:00

五、数据库/RAG 方案：如何写入记忆？

讲解要点

  • 历史对话本质上也是文本，因此可以像公司文档一样入库。
  • 长消息可以按段落或字数切成 chunk。
  • chunk 中应加入元信息，例如 topic、用户偏好、时间、来源、约束。
  • Elasticsearch 这类系统可同时支持 BM25 关键词、向量检索与混合搜索。
思路解析：写入侧的关键不是“存进去”这么简单，而是把未来检索时需要用到的线索一起结构化保存。元信息的质量会直接影响召回质量。

10:00 - 12:37

六、数据库/RAG 方案：如何读取记忆？

讲解要点

  • 直接检索：把用户 query embedding 后去数据库召回，或用分词/BM25 搜索。
  • Agent 检索：让 LLM 分析 query，生成关键词，检索后再判断是否足够，必要时 refine query。
  • 直接检索快、便宜；Agent 检索更智能，但增加 token 成本和延迟。
思路解析：读取侧体现了第一个核心 trade-off：速度与智能。系统可以根据场景选择固定检索链路，也可以让 LLM 参与规划与反思。

12:37 - 17:10

七、Markdown 方案：Memory / Topics / Transcript 三层

讲解要点

  • Memory：长期、跨会话、几乎一直生效，例如用户偏好、项目简介、全局约束。
  • Topics：按话题保存，例如 database deployment、frontend design；只有相关时加载。
  • Transcript：原始消息层，用于兜底和回溯。
思路解析：这个分层的核心，是让不同价值密度的信息进入不同加载路径：Memory 常驻但必须轻，Topics 相关时再加载，Transcript 不常用但保留证据链。

17:10 - 20:16

八、Markdown 记忆如何更新：先结构化，再落盘

讲解要点

  • Markdown 是纯文本，但可用标题和列表表达结构。
  • 更稳的做法不是让 LLM 随意编辑文件，而是加载后解析成 dict/JSON。
  • 新增对话经过 distill 生成结构化数据，再与原结构合并。
  • 最后再把结构化对象渲染回 Markdown。
思路解析：这是一条很重要的工程经验：对人可读的是 Markdown，对程序可控的是结构化对象。直接让模型改文本容易造成 key 漂移、重复、错位和难以 merge。

20:16 - 24:25

九、预定义 Key vs LLM 动态 Key：冰与火的 trade-off

讲解要点

  • 预定义 Key 代表“冰”：稳定、可控、容易 merge，但灵活性弱。
  • LLM 动态 Key 代表“火”：灵活、能适应新情况，但容易出现同义词漂移。
  • 例如 profile 与 overview 可能语义接近，focus 可能是新 key；系统需要判断是合并还是追加。
  • 实际系统通常采用中间方案：核心 key 预定义，同时保留有限的动态扩展空间。
思路解析：这是整期视频最关键的设计点之一。Memory 系统不是只靠 LLM 总结就能稳定运行，它还需要 schema、merge 策略、异常修正和版本演进机制。

24:25 - 27:35

十、Topics 如何被发现？Memory 为什么必须轻量？

讲解要点

  • Memory 永远加载，所以不能太长。
  • Topics 只在相关任务中加载，因此可以承载更具体、更长的上下文。
  • Agent 可以通过工具搜索 Markdown 文件来发现 topics。
  • 也可以在 Memory 中维护轻量 known topics 列表，让模型提前知道有哪些可加载话题。
思路解析：最后的结论回到系统设计：Memory 不是一个单文件，而是一套索引、摘要、主题、原始记录和加载策略共同组成的系统。好的 Memory 设计，会显著决定 Agent 是否长期好用。

核心结论

  1. LLM 原生没有真正的会话记忆，Agent Memory 是产品与工程层补上的能力。
  2. 长上下文不是万能解，窗口长度、注意力扩散、成本和延迟都需要被管理。
  3. 滑动窗口只能解决容量，不能解决“旧但重要”的长期信息。
  4. RAG 与 Markdown 分层不是互斥方案，可以组合使用：RAG 负责召回，Markdown 负责长期结构化沉淀。
  5. Memory 的 schema 与 Key 策略决定了系统长期是否稳定。
