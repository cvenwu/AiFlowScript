Model Context Protocol（MCP）从入门到精通

一份给后端工程师看的 MCP 实战与原理手册：协议层、传输层、SDK、内部实现、上下游交互全链路图，以及 Python 代码示例。 以 2025-11-25 规范版本为基线，兼顾 2025-06-18 与 2025-03-26 仍在普遍使用的实现。

1. MCP 是什么 & 为什么

Model Context Protocol（MCP） 是 Anthropic 于 2024 年 11 月开源的一套用于 LLM 应用与外部上下文/工具进行连接的开放协议。 它在 Host（宿主应用）⇄ Server（上下文/工具提供方） 之间定义统一的 RPC 接口，目标是把"接 N 个模型 × M 个工具"的 N×M 集成爆炸降为 N+M。

用一句话理解

"给 AI 应用的 USB-C 口"：任何遵循协议的 Server 都能即插即用地被任何遵循协议的 Host（Claude Desktop、Cursor、VS Code、Cline、自研 Agent…）使用。

后端视角的等价物

MCP ≈ 面向 LLM 的 OpenAPI/gRPC：JSON-RPC 2.0 报文 + 标准化的方法名 + 可发现的能力清单 + 会话生命周期 + 多种传输绑定。

什么场景该用 MCP

  • 给 LLM Agent 暴露受控的工具（数据库查询、内部 API 调用、文件读写、SaaS 操作）。
  • 给 LLM 暴露只读上下文（业务文档、配置、知识库、运行时状态）。
  • 统一公司内部 Agent 平台：一次实现，多 Host 复用（IDE、桌面、Web、CI）。
  • 跨进程/跨主机交付能力：本地命令行子进程，或远程 HTTPS Server。

什么场景不该用 MCP

  • 系统间纯后端通信、无 LLM 参与 → 直接用 gRPC/HTTP 即可，MCP 没必要。
  • 高吞吐流式数据管道 → JSON-RPC + SSE 不是为此设计的。
  • 非交互式批处理 → 用普通脚本/调度即可。

2. 心智模型与术语

术语含义后端工程师类比

flowchart LR subgraph HostApp["Host: AI 应用 (Claude Desktop / 自研 Agent)"] LLM["LLM 推理"] C1["MCP Client #1"] C2["MCP Client #2"] C3["MCP Client #3"] end S1["Server: Git/FS\n(stdio 子进程)"] S2["Server: 内部 API\n(Streamable HTTP)"] S3["Server: 数据库\n(stdio 子进程)"] LLM <--> C1 <--> S1 LLM <--> C2 <--> S2 LLM <--> C3 <--> S3

3. 5 分钟 Hello World（Python）

用 mcp 官方 Python SDK 的 FastMCP 高层封装。

安装

# 推荐 uv（也可 pip）
uv init mcp-hello && cd mcp-hello
uv add "mcp[cli]"

server.py

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("hello-server")

@mcp.tool()
def add(a: int, b: int) -> int:
    """两数相加。"""
    return a + b

@mcp.resource("greeting://{name}")
def greeting(name: str) -> str:
    """返回一句问候，作为只读上下文。"""
    return f"Hello, {name}!"

@mcp.prompt()
def code_review(language: str, code: str) -> str:
    """生成一个代码审查 Prompt。"""
    return f"请审查以下 {language} 代码并指出问题：\n\n```{language}\n{code}\n```"

if __name__ == "__main__":
    mcp.run()  # 默认 stdio

用官方 Inspector 调试

uv run mcp dev server.py
# 浏览器会打开 Inspector，可逐个调用 tools/resources/prompts

接入 Claude Desktop（macOS）

最小 Client（Python）

import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def main():
    params = StdioServerParameters(command="python", args=["server.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            tools = await session.list_tools()
            print([t.name for t in tools.tools])  # ['add']
            r = await session.call_tool("add", {"a": 1, "b": 2})
            print(r.content)  # [TextContent(text='3')] / structured

asyncio.run(main())

5. JSON-RPC 2.0 消息层

所有消息都遵循 JSON-RPC 2.0，jsonrpc:"2.0" 固定。三类消息：

  • Request：含 id + method + params，对端必须回应。
  • Response：含 id + (result 或 error)。
  • Notification：含 method + params 但无 id，对端不应回应。

常用方法一览（核心）

方向方法用途
C→Sinitialize协议版本与能力协商
C→Snotifications/initialized客户端已就绪
C→Sping心跳
C→Stools/list / tools/call列出/调用工具
C→Sresources/list / resources/templates/list / resources/read / resources/subscribe资源发现、读取与订阅
C→Sprompts/list / prompts/get列出/取得 Prompt
C→Scompletion/complete参数自动补全
C→Slogging/setLevel设置 Server 日志级别
S→Csampling/createMessage请 Host 调一次 LLM
S→Celicitation/create请 Host 向用户问问题
S→Croots/list问 Host 当前允许的文件/URI 边界
S→Cnotifications/tools/list_changed 等能力变更广播
S→Cnotifications/resources/updated订阅资源变化推送
S→Cnotifications/progress长任务进度
S→Cnotifications/message日志/调试输出

报文示例

initialize 请求

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "roots": { "listChanged": true },
      "sampling": {},
      "elicitation": {}
    },
    "clientInfo": { "name": "my-host", "version": "0.1.0" }
  }
}

initialize 响应

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "tools": { "listChanged": true },
      "resources": { "subscribe": true, "listChanged": true },
      "prompts": { "listChanged": true },
      "logging": {}
    },
    "serverInfo": { "name": "hello-server", "version": "0.1.0" },
    "instructions": "可选：给模型的 system 提示。"
  }
}

tools/call 请求

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "add",
    "arguments": { "a": 1, "b": 2 }
  }
}

tools/call 响应

{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "content": [
      { "type": "text", "text": "3" }
    ],
    "structuredContent": { "result": 3 },
    "isError": false
  }
}
错误处理：Server 端运行抛错应该以 result.isError = true 加 content 返回，而不是 JSON-RPC error 字段。error 留给协议级别错误（方法不存在、参数错、未授权等）。这样模型可以"看到"错误并自行重试。

6. 生命周期与能力协商

MCP 是有状态的协议。一条连接的生命周期分三段：

sequenceDiagram autonumber participant H as Host (Client) participant S as Server Note over H,S: 1) Initialization 阶段 H->>S: initialize(protocolVersion, capabilities, clientInfo) S-->>H: result(protocolVersion, capabilities, serverInfo, instructions?) H->>S: notifications/initialized Note over H,S: 2) Operation 阶段（可并发多次往返） H->>S: tools/list S-->>H: tools[] H->>S: tools/call(name, arguments) S-->>H: content[] / structuredContent S-->>H: notifications/progress (可选) S-->>H: notifications/tools/list_changed (能力变更) Note over H,S: 3) Shutdown 阶段 H->>S: 关闭传输 (stdio 关 stdin / HTTP DELETE 会话)

能力协商的关键点

  • protocolVersion：按日期版本（如 2025-06-18、2025-11-25）协商；不兼容则关闭连接。
  • capabilities：双向声明"我支持什么 + 是否会发 listChanged 通知"。Server 不会调用没声明的 Client 能力，反之亦然。
  • instructions：Server 可返回一段建议给模型，作为 system 增强。
易踩坑：在 initialize 完成 + 客户端发 notifications/initialized 之前，除 ping 与 logging 之外不应发其他请求。很多 Server 实现会拒绝。

7. 传输层：stdio 与 Streamable HTTP

MCP 规范定义了两种标准传输。自定义传输也允许，只要保留 JSON-RPC 报文语义。

7.1 stdio（本地子进程）

  • Host 把 Server fork 为子进程，stdin / stdout 用 换行分隔的 JSON-RPC（NDJSON）通信。
  • Server 写到 stdout 的内容必须只能是合法 MCP 报文，不允许 print 调试输出污染。
  • 调试/日志统一走 stderr，由 Host 决定丢弃还是转发。
  • 关闭：Host 关 stdin → Server 优雅退出。
sequenceDiagram participant H as Host participant OS as 操作系统 participant SP as Server 子进程 H->>OS: spawn("python server.py") OS-->>H: stdin/stdout/stderr 管道 H->>SP: 写入 JSON-RPC + "\n" (stdin) SP-->>H: JSON-RPC + "\n" (stdout) SP-->>H: 日志文本 (stderr, 可选) H->>SP: 关闭 stdin SP-->>OS: 退出

7.2 Streamable HTTP（远程 / 网关）

2025-03-26 引入，替代旧的 "HTTP + SSE" 双端点方案。核心：一个端点同时承载 POST 与 GET，按需升级为 SSE。

项规范要求
端点单 URL，如 https://example.com/mcp，支持 POST 与 GET
Client→Server每条 JSON-RPC 是一个新的 HTTP POST；Accept: application/json, text/event-stream
Server 回若包含 request：返回 application/json（一次性）或 text/event-stream（流式，可推中间通知 / 进度）；若只包含通知/响应：返回 202 Accepted
Server 主动推Client 可发 GET 打开常驻 SSE，由 Server 推 sampling/elicitation/通知；不支持就回 405
Sessioninitialize 响应头里下发 Mcp-Session-Id；后续每个请求都要回带；DELETE 主动关闭
版本协商请求头 MCP-Protocol-Version（2025-06-18+ 引入）
断线续传SSE 事件可带 id:，断线重连用 Last-Event-ID 续推
安全必须校验 Origin 防 DNS rebinding；本地启动时绑 127.0.0.1；建议 OAuth
sequenceDiagram autonumber participant C as Client participant N as 反向代理/网关 participant S as MCP Server C->>N: POST /mcp initialize (Accept: application/json, text/event-stream) N->>S: 转发 S-->>N: 200 application/json + Mcp-Session-Id: abc N-->>C: 200 + Header C->>N: POST /mcp tools/call (Mcp-Session-Id: abc) N->>S: 转发 S-->>N: 200 text/event-stream S-->>C: event: progress (id=1) S-->>C: event: progress (id=2) S-->>C: event: response (id=3) [tools/call result] C->>N: GET /mcp (Mcp-Session-Id: abc, Accept: text/event-stream) N->>S: 升级 SSE S-->>C: event: sampling/createMessage (server-initiated request) C-->>S: POST /mcp (response, Mcp-Session-Id: abc) C->>N: DELETE /mcp (关闭会话)
为什么从 HTTP+SSE 改成 Streamable HTTP？
  • 旧方案要起两个端点（POST 写、SSE 读），无法穿过普通负载均衡器，且鉴权语义混乱。
  • 新方案单端点 + 普通 HTTP 语义，CORS、Bearer、API Gateway、CDN 都能正常用。
  • SSE 仅在需要推送时升级，是"可选流式"而不是"强制流式"。

7.3 选哪种传输？

场景传输理由
本地工具（FS、Git、SQLite）stdio零网络、零鉴权、生命周期跟随宿主

8. 授权与安全模型

  • stdio：信任边界 = 操作系统进程；Host 决定是否启动该 Server。授权依靠环境变量/本地配置。
  • Streamable HTTP：规范要求/推荐 OAuth 2.1（含 PKCE）；Bearer Token 走标准 Authorization 头。可走 API Key/Header 等自定义方式，但不应把 token 放在 query string。
  • 同源/防 rebinding：本地起 HTTP Server 必须校验 Origin 并绑 127.0.0.1。
  • 会话 ID：服务端可加密绑定用户身份；DELETE 用于注销。
  • 工具最小权限原则：每个 Tool 应该显式声明副作用（annotations.destructiveHint / readOnlyHint / openWorldHint / idempotentHint），Host 据此决定是否需要用户确认。
真实世界安全风险：
  • Prompt Injection via Tool Output：Tool 把外部内容回吐到模型，可被注入指令。要在 Host 侧做内容隔离 / re-prompt。
  • Confused Deputy：Server 拿着用户 token 替模型做不该做的事。Tool 应在 Server 内部强校验，不依赖模型自律。
  • Rug Pull：远程 Server 的 Tool schema 与 description 中途被替换为恶意版本。Host 应做能力指纹/审计。

9. Tools（工具）

Tool 是给模型调用的函数：输入 schema、输出 content，可带副作用。

Tool 定义关键字段

字段说明
name唯一标识，建议 snake_case，模型会看到
title展示名，UI 用
description给模型看的说明，决定模型何时调用
inputSchemaJSON Schema，越严格越好（含 enum、min/max、required）
outputSchema结构化输出 schema，配合 structuredContent
annotationsreadOnlyHint / destructiveHint / idempotentHint / openWorldHint

Python 示例（含错误返回）

from typing import Annotated
from pydantic import Field
from mcp.server.fastmcp import FastMCP
from mcp.types import TextContent

mcp = FastMCP("billing")

@mcp.tool(
    annotations={
        "title": "退款",
        "readOnlyHint": False,
        "destructiveHint": True,
        "idempotentHint": True,
    }
)
def refund(
    order_id: Annotated[str, Field(pattern=r"^ord_[a-z0-9]{16}$")],
    amount_cents: Annotated[int, Field(gt=0, le=1_000_000)],
    reason: str,
) -> str:
    """对指定订单发起退款。amount_cents 不能超过订单原金额。"""
    try:
        do_refund(order_id, amount_cents, reason)
        return f"refunded {amount_cents} cents on {order_id}"
    except DomainError as e:
        # 让模型自己看到错误并可能重试
        raise ToolError(str(e))

10. Resources（资源）

Resource 是只读的上下文，按 URI 寻址；可静态可模板化，可订阅变更。

  • resources/list 返回静态资源列表；resources/templates/list 返回 URI 模板（含 {var}）。
  • resources/read 按 URI 拿内容；返回 contents[]，每项含 uri + mimeType + text/blob。
  • resources/subscribe + notifications/resources/updated 实现增量推送。
@mcp.resource("config://app/{env}")
def app_config(env: str) -> str:
    """按环境读取应用配置（只读）。"""
    return json.dumps(load_config(env))

@mcp.resource("file:///logs/today.log")
def today_log() -> str:
    return open("/var/log/today.log").read()
Tool vs Resource 怎么选？
  • 有副作用 / 需要参数推理 → Tool。
  • 纯读、URI 可枚举、模型很可能"自动注入" → Resource。
  • 实操中很多人全部塞 Tool 没问题，但放 Resource 的好处是 Host 可以做"@提及"/自动注入。

11. Prompts（提示模板）

Prompt 是由 Server 维护、由用户主动选用的模板（典型形态：IDE 里的 slash command）。

@mcp.prompt(title="生成 SQL")
def gen_sql(table: str, intent: str) -> list[dict]:
    return [
        {"role": "system", "content": "你是资深 DBA。"},
        {"role": "user", "content": f"基于表 {table}，{intent}，给出 PostgreSQL SQL。"},
    ]

Prompt 在 Host 里通常以"/命令"形式展示，跟 Tool（模型自己决定调）形成互补。

12. Sampling / Elicitation / Roots（反向能力）

Sampling

Server 调 sampling/createMessage 让 Host 帮自己跑一次 LLM。用途：Server 内部需要 LLM 但又不想自己接 API/付钱。Host 会向用户征求同意。

Elicitation

Server 调 elicitation/create 弹窗向用户问问题（带 schema）。用途：缺参补全、二次确认、敏感操作授权。

Roots

Host 通过 roots/list 告诉 Server 允许访问的工作目录/URI 边界。Server 端 FS/Git 类工具应严格遵守。

sequenceDiagram participant U as 用户 participant H as Host participant S as Server S->>H: sampling/createMessage(messages, modelHints) H->>U: 弹窗：是否允许 Server 使用 LLM？ U-->>H: 允许 H->>H: 调 LLM H-->>S: result(content[])

13. Server 内部实现剖析

以 mcp Python SDK 的 FastMCP 为蓝本，拆解 Server 端"接收一条 JSON-RPC 到返回结果"的全过程。

flowchart TB IN["传输层 in\n(stdin 行 / HTTP POST)"] --> P["JSON 反序列化\n+ JSON-RPC 校验"] P --> R["路由 dispatcher\n按 method 分发"] R -->|"initialize"| L["LifecycleHandler\n→ 协商版本/能力"] R -->|"tools/list"| TL["枚举注册表"] R -->|"tools/call"| TC["参数 schema 校验\n(JSON Schema → pydantic)"] TC --> EX["执行用户 handler\n(同步函数 / async)"] EX --> CV["返回值规整\n→ content[] / structuredContent"] CV --> ENC["JSON 序列化\n+ id 回填"] ENC --> OUT["传输层 out\n(stdout 行 / HTTP body / SSE event)"] EX -.通知/进度.-> OUT L --> OUT TL --> ENC

核心数据结构

  • Server 实例：持有 ToolRegistry、ResourceRegistry、PromptRegistry，每个 registry 是 name → metadata + callable 的字典。
  • Session 状态机：uninitialized → initializing → ready → closing。在 ready 之前，除 initialize/ping 外的请求都会被拒绝。
  • Schema 推导：FastMCP 用类型注解 + pydantic 自动把函数签名→ inputSchema。返回值若为 BaseModel，则自动填 outputSchema。
  • Context 对象：handler 可注入 Context，里面有 session.send_log_message(), session.create_message()（反向 sampling），request_context，用于在 Tool 内部反向调 Client。

同步/异步两条路径

Python SDK 内部用 anyio 任务组并发：一个任务从传输层读，一个任务调度 handler 执行，handler 完成后把结果丢回 outbox。这样长任务可以并行发 notifications/progress。

能力变更通知

Server 在运行时新增/删除工具时，必须已经在 initialize 响应中声明 tools.listChanged:true，然后用 notifications/tools/list_changed 通知。Client 收到后会重新拉 tools/list。

伪代码：极简 Server（自己手写，不依赖 SDK） 
import sys, json

TOOLS = {
  "add": {
    "name": "add",
    "description": "Add two numbers",
    "inputSchema": {"type":"object","properties":{"a":{"type":"number"},"b":{"type":"number"}},"required":["a","b"]},
  }
}

def call_tool(name, args):
    if name == "add": return args["a"] + args["b"]
    raise ValueError("unknown tool")

state = "uninit"
for line in sys.stdin:
    req = json.loads(line)
    rid = req.get("id")
    m = req["method"]
    if m == "initialize":
        state = "initializing"
        resp = {"jsonrpc":"2.0","id":rid,"result":{
            "protocolVersion":"2025-06-18",
            "capabilities":{"tools":{"listChanged":False}},
            "serverInfo":{"name":"tiny","version":"0.0.1"}
        }}
    elif m == "notifications/initialized":
        state = "ready"; continue  # 无 id 不回
    elif m == "tools/list":
        resp = {"jsonrpc":"2.0","id":rid,"result":{"tools":list(TOOLS.values())}}
    elif m == "tools/call":
        out = call_tool(req["params"]["name"], req["params"]["arguments"])
        resp = {"jsonrpc":"2.0","id":rid,"result":{
            "content":[{"type":"text","text":str(out)}],
            "structuredContent":{"result":out},
            "isError":False}}
    else:
        resp = {"jsonrpc":"2.0","id":rid,"error":{"code":-32601,"message":"Method not found"}}
    sys.stdout.write(json.dumps(resp)+"\n"); sys.stdout.flush()

14. Client / Host 内部实现剖析

flowchart TB subgraph Host["Host 进程"] AL["Agent Loop / Orchestrator"] LM["LLM Adapter (Anthropic / OpenAI / 自研)"] CM["ClientManager (多 Server 多连接)"] subgraph PerConn["每个 Server 一个 Client"] RD["Reader 任务: 解析帧"] WT["Writer 任务: 发帧"] ST["Session State + Pending Map"] TR["Transport: stdio/http"] end AL --> LM AL <--> CM CM <--> PerConn RD <--> ST WT <--> ST ST <--> TR end

关键机制

  • Request/Response 关联：每发一条 request 生成单调递增 id，Pending Map: id → Future。收到响应按 id 唤醒。
  • 反向请求：Server 也可以发请求（sampling/elicitation/roots/list），Client 用同一套 dispatcher，按 method 路由到 Host 注入的回调。
  • 能力门控：Client 在调任何方法前先检查 serverInfo.capabilities，没声明就不调，避免 -32601。
  • 转发到 LLM：Host 把 tools/list 结果转换为 LLM provider 的 tool schema（Anthropic Messages、OpenAI function calling、Gemini function declaration）；LLM 决定调用时，再 tools/call 回 Server，把结果作为 tool message 喂回模型。
  • 多 Server 命名空间：建议给 Tool 加 serverName.toolName 前缀，避免不同 Server 重名。
Host 端 Agent Loop 伪代码（接 Anthropic Claude） 
tools_for_llm = []
for srv in clients:
    for t in (await srv.list_tools()).tools:
        tools_for_llm.append({
            "name": f"{srv.name}__{t.name}",
            "description": t.description,
            "input_schema": t.inputSchema,
        })

messages = [{"role":"user","content": user_input}]
while True:
    resp = anthropic.messages.create(model="claude-...", tools=tools_for_llm, messages=messages)
    messages.append({"role":"assistant","content": resp.content})
    tool_uses = [b for b in resp.content if b.type == "tool_use"]
    if not tool_uses:
        break
    tool_results = []
    for tu in tool_uses:
        srv_name, tool_name = tu.name.split("__", 1)
        srv = clients[srv_name]
        r = await srv.call_tool(tool_name, tu.input)
        tool_results.append({"type":"tool_result","tool_use_id":tu.id,
                             "content": r.content, "is_error": r.isError})
    messages.append({"role":"user","content": tool_results})

放在网关后面（推荐拓扑）

flowchart LR Cli["Host / MCP Client"] CDN["CDN / WAF"] GW["API Gateway\n(鉴权/限流/日志)"] Auth["IdP / OAuth 2.1"] K8s["MCP Server 集群\n(无状态 + Session 粘性)"] Redis[("Redis\nSession & Pub/Sub")] DB[("业务 DB")] API[("内部 API")] Cli --> CDN --> GW GW --> Auth GW --> K8s K8s <--> Redis K8s --> DB K8s --> API

17. 嵌入 LLM 的 Host（自研 Agent）

import asyncio
from contextlib import AsyncExitStack
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client
from mcp.client.streamable_http import streamablehttp_client

class MCPHub:
    def __init__(self):
        self.sessions: dict[str, ClientSession] = {}
        self.stack = AsyncExitStack()

    async def add_stdio(self, name, command, args):
        params = StdioServerParameters(command=command, args=args)
        read, write = await self.stack.enter_async_context(stdio_client(params))
        sess = await self.stack.enter_async_context(ClientSession(read, write))
        await sess.initialize()
        self.sessions[name] = sess

    async def add_http(self, name, url, headers=None):
        read, write, _ = await self.stack.enter_async_context(
            streamablehttp_client(url, headers=headers or {})
        )
        sess = await self.stack.enter_async_context(ClientSession(read, write))
        await sess.initialize()
        self.sessions[name] = sess

    async def all_tools(self):
        tools = []
        for name, s in self.sessions.items():
            for t in (await s.list_tools()).tools:
                tools.append((name, t))
        return tools

    async def call(self, server, tool, args):
        return await self.sessions[server].call_tool(tool, args)

    async def aclose(self):
        await self.stack.aclose()

18. 调试、可观测与部署

调试工具

  • MCP Inspector（官方 GUI/CLI）：npx @modelcontextprotocol/inspector 或 uv run mcp dev server.py，可视化所有报文，单步调 Tool。
  • mitmproxy/HTTP 抓包：Streamable HTTP 用普通 HTTPS 工具就能调。
  • stderr 日志：stdio Server 把日志写 stderr，由 Host 转发到 notifications/message 或本地文件。

可观测三件套

  • Trace：每条 JSON-RPC 加 W3C traceparent（自定义 meta 字段），Server 端继续传播到下游。
  • Metric：mcp_tool_call_total{tool=...,status=...}、mcp_tool_call_duration_seconds、mcp_session_active。
  • Audit Log：记录 session_id, user_id, tool, arguments(hashed), result_summary，用于事后审计与合规。

容器化 & 灰度

  • Server 容器化时不要把 stdio Server 直接对外，应该用 Streamable HTTP；stdio 留给桌面/IDE。
  • Schema/能力变更属于面向模型的 API 变更，按版本灰度，并在 instructions 里写清楚迁移指引。
