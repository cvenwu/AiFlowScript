一、视频概览区

基础信息

  • 视频标题：【2026必学！】LlamaIndex 自主式 RAG，比传统 RAG 强 10 倍的检索方案
  • 本 P 标题：4-构建代理推理循环
  • 核心主题：用 LlamaIndex 构建支持多步工具调用、记忆、调试和人类反馈的 Agent reasoning loop。
  • 内容类型：代码实操 + 架构讲解 + API 演示。

10 秒核心要点

  1. 传统 RAG 的单次工具调用不够处理复杂问题，复杂问题需要多步规划、检索和综合。
  2. Agent reasoning loop 的本质是：选择工具 → 调用工具 → 观察结果 → 决定下一步或最终回答。
  3. LlamaIndex 中 Agent 由 AgentWorker 和 AgentRunner 两层组成，分别负责单步执行与整体调度。
  4. query 适合一次性查询，chat 可以保留对话历史，支持“上述内容”这类上下文引用。
  5. 低层 API 让开发者可以逐步执行、检查 completed/upcoming steps，并在中途注入用户反馈。

三、分章节详细解读

1. 00:00-00:39｜为什么需要完整 Agent reasoning loop

开场先回顾前几节课：此前查询流程都是一次性的 forward pass——给定查询，选择正确工具、传入参数、得到响应。但作者马上指出：这种方式 对复杂问题和模糊问题都有限制。

  • 复杂问题可能包含多个子步骤，不能只靠一次检索或一次摘要回答。
  • 模糊问题可能需要进一步澄清，或者先检索一部分信息再决定下一步。
  • 本节目标是定义一个完整的 agent reasoning loop，让 Agent 能在多步中围绕工具进行推理。
  • 采用的是 function calling agent，也就是原生集成 LLM function calling 能力的 Agent 实现。
关键结论：Agent 的升级点不只是“会调用工具”，而是能在多轮中决定“下一步该调用什么工具、是否继续、何时输出最终答案”。

2. 00:39-02:34｜环境准备与 Agent 两层组件

作者沿用前两节课的 MetaGPT 论文，暂时仍是单文档场景；下一节才扩展到多文档。本节复用上节的两个工具：auto-retrieval vector search tool 和 summarization tool，并把工具构造封装进 utils 模块。

from helper import get_openai_api_key
OPENAI_API_KEY = get_openai_api_key()

import nest_asyncio
nest_asyncio.apply()

from utils import get_doc_tools
vector_tool, summary_tool = get_doc_tools("metagpt.pdf", "metagpt")

from llama_index.llms.openai import OpenAI
llm = OpenAI(model="gpt-3.5-turbo", temperature=0)

随后作者解释 LlamaIndex 中 Agent 的两个核心部分：

组件职责理解方式
AgentWorker执行给定 Agent 的下一步：基于历史、记忆、状态和当前输入，决定调用哪个工具、如何调用，以及是否返回最终答案。单步推理与执行器。
AgentRunner创建任务、调度 AgentWorker 在任务上连续运行，并最终把响应返回给用户。整体任务调度器。
from llama_index.core.agent import FunctionCallingAgentWorker
from llama_index.core.agent import AgentRunner

agent_worker = FunctionCallingAgentWorker.from_tools(
    [vector_tool, summary_tool],
    llm=llm,
    verbose=True,
)
agent = AgentRunner(agent_worker)

verbose=True 的作用是观察中间输出，这对后面理解 reasoning loop 非常关键。

3. 02:34-04:47｜高层 query 接口：复合问题如何被拆成多步

作者首先使用高层接口 agent.query，提出一个复合问题：

response = agent.query(
    "Tell me about the agent roles in MetaGPT, "
    "and then how they communicate with each other."
)

这个问题包含两个子任务：

  1. MetaGPT 中有哪些 agent roles？
  2. 这些角色之间如何通信？

运行结果显示，Agent 会先把问题拆解：第一步围绕「agent roles in MetaGPT」调用 summary_tool。作者也提醒：summary tool 未必是最精准的工具；vector tool 可能返回更精确的上下文。但 summary tool 仍是合理选择，而更强模型（如 GPT-4 Turbo、Claude 3 Sonnet/Opus）可能做出更精准的工具选择。

得到角色信息后，Agent 再触发第二个问题：角色之间的通信机制。最终它把整个对话历史结合起来，生成完整回答：MetaGPT 中角色包括产品经理、架构师、项目经理、QA 工程师等，并以顺序协作方式遵循标准操作流程，通过共享消息角色和订阅机制通信。

source_nodes 溯源

多步查询不能只看最终答案，还要确认每一步信息来源。作者展示可以通过 response.source_nodes 查看检索到的来源节点内容：

response.source_nodes[0].get_content()

这一步解决的是 RAG 工程中的可信度问题：Agent 多步推理越复杂，越需要可追踪来源。

4. 04:47-06:21｜chat 接口与对话记忆

作者指出：agent.query 是一次性查询，不保留状态。接下来换成 agent.chat，展示 Agent 如何维护对话历史。

默认情况下，Agent 会把聊天保存在 conversational memory buffer 中。这个 memory 模块可以自定义；默认是一个随着 LLM 上下文窗口大小滚动的扁平列表。于是，当 Agent 决定使用工具时，它不仅看当前输入，也看之前的对话历史。

response = agent.chat("Tell me about the evaluation datasets used.")
response = agent.chat("Tell me the results over one of the above datasets.")

第一问中，Agent 调用 summary tool，回答 MetaGPT 使用了 HumanEval、MBPP、SoftwareDev 等评估数据集。第二问中的「above datasets」依赖前文；Agent 能结合对话历史，把它转换成具体查询，例如对 HumanEval 数据集结果的 vector_tool 检索。

关键结论：chat 的价值不是“对话界面更自然”，而是让 Agent 的工具选择受到历史上下文影响，从而支持连续追问。

5. 06:21-09:57｜低层 Agent 控制：调试、可控性与逐步执行

作者进入下一部分：不仅使用高层研究助手式接口，还要能更细粒度地控制 Agent。这对两个场景特别重要：

  • 可调试性：开发者可以看到 Agent 每一步到底发生了什么，哪里失败，能否通过不同输入改变执行路径。
  • 可操控性 / 更丰富 UX：产品可以在 Agent 执行中途监听人类反馈，必要时中断或修改执行，而不是等任务完成后才反馈。

低层 API 的基本流程如下：

task = agent.create_task(
    "Tell me about the agent roles in MetaGPT, "
    "and then how they communicate with each other."
)

step_output = agent.run_step(task.task_id)

create_task 会返回 task object，其中包含用户输入和附加状态；run_step 只执行这个任务的一步，并返回 step output。

第一步执行后，Agent 调用 summary_tool 查询 MetaGPT 中的 agent roles，并停止在这里。随后作者展示如何检查已完成步骤：

completed_steps = agent.get_completed_steps(task.task_id)
print(len(completed_steps))

也可以检查接下来还有哪些待执行步骤：

upcoming_steps = agent.get_upcoming_steps(task.task_id)
print(f"Num upcoming steps for task {len(upcoming_steps)}")

这里的 upcoming step 输入为 None，原因是 Agent 会从 conversation history 自动生成下一步 action，不需要外部额外输入。

6. 09:57-11:37｜中途注入用户反馈与最终响应合成

作者强调低层接口的一个好处：如果想暂停，现在就可以暂停，直接拿到中间结果，而不必完成整个 Agent flow。随后继续运行，并演示插入用户输入：

# 伪代码表达视频中的操作意图
# 在任务执行中途向 memory 添加用户消息：
"What about how agents share information?"

这个输入并不属于原始任务，但注入后会改变 Agent 的后续执行：下一次调用变成查询「agents in MetaGPT 如何共享信息」。这正是 steerability 的体现。

当整体任务大致完成后，还需要运行最后一步来综合答案。作者用 step_output.is_last 检查这是否是最后一步；确认之后调用：

response = agent.finalize_response(task.task_id)

结尾总结：本节学到了 Agent 的高层接口和低层调试接口；下一节将把 Agent 扩展到多文档场景。

四、结尾总结与价值提炼

核心内容复盘

  • 问题：单次工具调用无法优雅处理多步骤或模糊查询。
  • 方案：用 function calling agent 构建多步 reasoning loop。
  • 组件：AgentWorker 执行下一步，AgentRunner 调度任务和返回最终响应。
  • 高层接口：query 适合一次性问题，chat 适合带历史的连续追问。
  • 低层接口：create_task / run_step / get_completed_steps / get_upcoming_steps / finalize_response 支持调试和控制。
  • 工程价值：能追踪 source_nodes，能查看中间步骤，能插入人类反馈。

落地行动建议

  1. 先把 RAG 工具封装成清晰的 tool schema：例如 vector_tool、summary_tool。
  2. 使用 verbose=True 或日志系统记录每次工具调用、参数、返回内容与最终合成过程。
  3. 对复杂问题优先采用 Agent loop，而不是强行一次检索后回答。
  4. 为生产系统增加最大步数、错误兜底和 source_nodes 展示，避免循环失控或不可解释。
  5. 如果做交互式产品，优先保留低层控制能力，支持暂停、人工反馈、重新规划和继续执行。

传统 RAG 与 Agentic RAG 的差异

维度传统单次 RAG本节展示的 Agentic RAG
执行方式一次检索 / 一次生成多步工具调用与观察循环
上下文主要依赖当前 query可结合 conversation history、memory、task state
可调试性通常只能看最终答案和检索片段可逐步查看 completed/upcoming steps
用户反馈多在任务完成后反馈可在执行中途注入，改变后续路径
