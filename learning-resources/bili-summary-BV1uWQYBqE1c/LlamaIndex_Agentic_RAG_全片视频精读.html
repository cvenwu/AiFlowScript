UP 主吴恩达AIAgent
总时长约 44:46（6 个分 P）
内容类型技术教程 / Agentic RAG 实操 / LlamaIndex 课程拆解
核心主题把传统 RAG 升级为能路由、调用工具、多步推理、多文档检索的自主研究代理
主要材料MetaGPT、LongLoRA、Self-RAG、SWE-bench 等 ICLR 2024 论文示例

核心要点速览

  • 传统 RAG 只做一次检索 + 一次生成，难以处理跨文档、多步骤、需中途决策的复杂研究问题。
  • Router 是最小 Agentic RAG：它让 LLM 根据问题在向量检索与摘要引擎之间做动态选择。
  • Tool Calling 是关键升级：LLM 不只选择函数，还能从自然语言中推断参数，例如页码过滤条件。
  • Agent 推理循环让工具调用多步化：能维护记忆、拆解任务、查看步骤，并允许人类中途注入反馈。
  • 多文档 Agent 的瓶颈不是文档，而是工具规模：用 ObjectIndex 检索相关工具，避免把几十上百个工具塞进提示词。

整体框架与知识结构

问题背景：复杂研究请求需要跨资料检索、逐步推理、动态调整检索目标，标准 RAG 不够。
第一层能力：Router：为同一文档构建 summary index 与 vector index，用 selector 选择合适查询引擎。
第二层能力：Tool Calling：把 Python 函数、向量检索、摘要能力封装成工具，让 LLM 选择工具并生成参数。
第三层能力：Agent Reasoning Loop：用 AgentWorker + AgentRunner 执行多步工具调用，支持记忆、调试和用户反馈。
第四层能力：Multi-document Agent：为每篇文档生成 vector/summary 工具，再通过 ObjectIndex 做“工具级检索”。

作者讲解逻辑

作者采用的是“先定义局限 → 再逐层加能力 → 最后处理规模化问题”的表达路径：

  1. 从传统 RAG 的单次调用局限引入：一次检索、一次 prompt、一次回答，适合简单问题，不适合复杂研究。
  2. 用 Router 建立最小决策闭环：让 LLM 在摘要与向量检索之间做选择，证明“RAG 流程可被动态编排”。
  3. 用 FunctionTool 解释工具调用本质：先用 add/mystery 玩具函数降低理解成本，再迁移到 metadata-filtered vector search。
  4. 把一次性工具调用扩展成 Agent 循环：引入 AgentWorker/AgentRunner、任务步骤、记忆、source nodes 与低层调试接口。
  5. 用多文档场景暴露新瓶颈：工具数量变多会导致上下文、成本、延迟和选择混乱，因此引入 ObjectIndex 检索工具。

1. 课程导入：为什么需要 Agentic RAG

00:00 - 02:51

开场由 Andrew Ng 与 LlamaIndex 联合创始人 Jerry Liu 引出课程目标：构建一个能在数据上进行高级工具使用、推理与决策的研究代理。传统 RAG 更适合“小规模文档 + 简单问题”：检索一些上下文，塞进 LLM prompt，然后调用一次模型得到回答。

但研究型问题通常不是单步的：例如先从一篇论文识别主题，再根据主题去其他论文中检索细节，早期步骤会影响后续步骤。课程因此规划了四个渐进能力：routing、tool use、multi-step reasoning with tool use、multi-document reasoning。

  • 目标不是替代 RAG，而是把 RAG 管线变成可被 Agent 调度的工具。
  • 课程强调可调试性：能查看 Agent 做了什么，并在中间步骤注入人类反馈。
  • 最终形态是一个更高级的研究助手，能够处理多文档、多步骤问题。

2. 路由器查询引擎：最简单的 Agentic RAG

02:51 - 12:01

第一课从最简单的 Agentic RAG 形式——Router——开始。给定一个查询，Router 会在多个 query engine 中选择一个来执行。作者用 MetaGPT 论文构建两个索引：Vector Index 用于检索具体上下文，Summary Index 用于对整篇文档进行总结。

summary_index = SummaryIndex(nodes)
vector_index = VectorStoreIndex(nodes)
summary_query_engine = summary_index.as_query_engine(use_async=True)
vector_query_engine = vector_index.as_query_engine()

每个 query engine 会进一步包装成 QueryEngineTool，并提供描述信息：summary tool 适合总结问题，vector tool 适合检索 MetaGPT 论文中的具体上下文。RouterQueryEngine 接收 selector 与工具列表，由 selector 选择应调用哪个工具。

  • 问“文档摘要是什么？”时，Router 选择 summary tool，并返回所有 chunk 参与总结。
  • 问“agents 如何共享信息？”时，Router 选择 vector tool，因为这是需要定位具体段落的问题。
  • 作者最后把流程封装成 get_router_query_engine(file_path)，方便换成自有 PDF。

3. 工具调用：让 LLM 选择工具并推断参数

12:01 - 22:13

第三分 P 的核心是：LLM 不再只是选择一个 query pipeline，还要推断函数参数。作者先用两个 Python 函数演示 FunctionTool：函数签名、类型注解和 docstring 会共同构成 LLM 理解工具用途的依据。

from llama_index.core.tools import FunctionTool

def add(x: int, y: int) -> int:
    """Adds two integers together."""
    return x + y

def mystery(x: int, y: int) -> int:
    """Mystery function that operates on top of two numbers."""
    return (x + y) * (x + y)

add_tool = FunctionTool.from_defaults(fn=add)
mystery_tool = FunctionTool.from_defaults(fn=mystery)

当用户问 What is the output of the mystery function on 2 and 9?，模型会选择 mystery，并推断 x=2, y=9，得到 121。这说明工具调用不只是“路由”，而是“路由 + 参数抽取”。

随后作者把这个机制迁移到 RAG：读取 MetaGPT PDF，切分为 nodes，并观察每个 node 的 metadata，尤其是 page_label。手动构造 MetadataFilters 后，向量检索可以被限制到某一页。

query_engine = vector_index.as_query_engine(
    similarity_top_k=2,
    filters=MetadataFilters.from_dicts([
        {"key": "page_label", "value": "2"}
    ])
)

视频最关键的封装是 vector_query(query, page_numbers)：LLM 从自然语言中抽取查询文本和页码，将页码转成 metadata filters，再执行向量检索。这样用户问“page 2 上 MetaGPT 的 high-level results”时，模型会自动传入 page_numbers=["2"]。

  • vector_tool：适合带具体条件、具体页码、具体事实的问题。
  • summary_tool：适合对整篇论文做整体总结。
  • 把两者一起交给 LLM 后，模型需要同时完成工具选择和参数推断。

4. 构建 Agent 推理循环：从单步调用到多步任务

22:13 - 33:52

第四课指出：此前查询都是 single forward pass，即给定 query，调用正确工具和参数，返回响应。但复杂问题可能包含多步骤或模糊需求，因此需要完整的 Agent reasoning loop。

LlamaIndex 中 Agent 由两个核心组件构成：

  • AgentWorker：负责在给定历史、记忆、状态和当前输入的情况下，决定下一步调用哪个工具、是否继续或返回最终结果。
  • AgentRunner：负责任务调度，创建 task，编排 AgentWorker 的多步运行，并向用户返回最终响应。
agent_worker = FunctionCallingAgentWorker.from_tools(
    [vector_tool, summary_tool],
    llm=llm,
    verbose=True
)
agent = AgentRunner(agent_worker)

示例问题是“告诉我 MetaGPT 中的 agent roles，以及它们如何互相通信”。Agent 会先用 summary tool 处理角色，再继续处理通信机制，最后综合对话历史生成最终回答。作者特别强调要检查 response.source_nodes，确保多步推理仍然可追溯。

接着作者展示低层控制接口：create_task、run_step、get_completed_steps、get_upcoming_steps、finalize_response。这些接口的价值有两点：

  • 可调试性：能暂停执行，检查中间步骤、已完成步骤、即将执行的步骤。
  • 可引导性：能在执行中注入用户输入，例如提醒 Agent 改查“agents 如何共享信息”。

作者还展示了对话记忆：用 agent.chat 代替一次性 agent.query 后，后续问题“one of the above datasets”能依赖前文提到的数据集。

5. 多文档代理：从 3 篇论文扩展到 11 篇论文

33:52 - 44:15

第五课把前面的单文档 Agent 扩展到多文档。作者先构建 3 篇论文场景：MetaGPT、LongLoRA、Self-RAG。每篇论文都通过 get_doc_tools 生成两个工具：一个 vector tool、一个 summary tool，因此三篇论文共有 6 个工具。

  • 可以问 LongLoRA 的评测数据集和结果。
  • 也可以同时要求总结 Self-RAG 与 LongLoRA，Agent 会分别调用两个 summary tool，再合成回答。

随后作者扩展到 11 篇 ICLR 2024 论文。此时会出现工具规模问题：如果每篇论文两个工具，11 篇就是 22 个；100 篇就是 200 个。直接把所有工具描述塞进 prompt 会带来三类问题：

  1. 上下文装不下：工具描述会占用大量 prompt token。
  2. 成本和延迟飙升：每次调用都要携带大量工具信息。
  3. LLM 容易选错：候选工具过多时，模型决策质量下降。

解决方案是做“工具级 RAG”：先检索相关工具，再把少量相关工具交给 Agent。LlamaIndex 用 ObjectIndex 把 Python 工具对象转换/序列化成可检索表示，并通过 object retriever 返回工具对象本身。

obj_index = ObjectIndex.from_objects(
    all_tools,
    index_cls=VectorStoreIndex
)
obj_retriever = obj_index.as_retriever(similarity_top_k=3)

最后两个比较查询验证了这种思路：比较 MetaGPT 与 SWE-bench 的 eval dataset，或比较 LongLoRA 与 LoftQ 的方法。Agent 先检索相关工具，再调用对应 summary/vector 工具，最终合成跨论文回答。

6. 结论与资源

44:15 - 44:46

结尾回顾了整门课：从 Router Agent 开始，经过 Tool Calling，再到能在单文档和多文档上推理的 Agent。作者建议如果要继续构建自定义 Agent、提交社区模板，或使用高级文档解析服务，可以参考 LlamaIndex 文档、LlamaHub Agent 模板和 LlamaParse/Cloud 服务。

结尾总结与价值提炼

核心知识清单

  • RouterQueryEngine：在多个 query engine 之间动态选择。
  • SummaryIndex vs VectorStoreIndex：整体总结与局部检索两种不同 retrieval behavior。
  • FunctionTool：把 Python 函数变成 LLM 可调用工具。
  • MetadataFilters：将自然语言条件转为结构化检索约束。
  • AgentWorker / AgentRunner：实现多步工具调用与任务编排。
  • Chat memory：让 Agent 能理解“上面提到的”这类依赖历史的问题。
  • ObjectIndex：把工具对象也纳入检索，解决多文档工具爆炸。

落地行动建议

  • 做单文档 QA 时，先配一对工具：vector tool + summary tool。
  • 如果用户问题类型差异明显，先用 Router；如果需要参数抽取，升级到 Tool Calling。
  • 为工具函数写清晰的类型注解和 docstring，因为它们会直接影响模型调用质量。
  • 调试 Agent 时不要只看最终答案，要看 tool call、参数、source nodes 与中间步骤。
  • 文档数量上来后，不要把所有工具塞给模型；优先做工具检索，再做 Agent 推理。
