从 Go 服务端到 FastAPI Agent Backend

用 4 周时间，从 FastAPI CRUD 演进到简化版 AI Agent 后端。每天约 2 小时，建立 Python Web 工程化、SSE 流式响应、Tool 抽象和面试可讲述项目经验。

Go 服务端工程师 FastAPI Agent Backend 每天约 2 小时 面试 / 转岗可讲述

当前起点

01

当前项目：fast-api-demo

起点项目是 fast-api-demo。它现在更像一个轻量 Python 脚手架，而不是完整后端服务：可以从最小入口开始，逐步加入 FastAPI 应用实例、路由、schema、测试、数据库和 Agent 领域模型。

路线不从复杂模板开始，而是让每次新增结构都能回答一个工程问题：为什么拆路由、为什么需要 service/repository、为什么需要 Conversation、Message 和 AgentRun。

02

当前 Python 水平：简单脚本

当前默认能力是能读写简单 Python 脚本，但还不熟悉 Python Web 工程化、包结构、类型注解、async/await、pytest 体系和 FastAPI 的依赖注入方式。

学习重点不是背 API，而是把 Go 服务端经验迁移过来：把 handler、service、dao、struct binding、goroutine、streaming response 等概念映射到 FastAPI 项目里的 routes、services、repositories、Pydantic、asyncio task 和 StreamingResponse / SSE。

03

最终目标：面试可讲的 Agent Backend

最终产物是一个小而完整的 FastAPI Agent Backend Demo：既能运行，也能测试，还能清楚讲出从 CRUD 后端到 Agent 后端的演进逻辑。

面试表达要覆盖三层价值：FastAPI 基础能力、Python 服务端工程能力、AI Agent 后端能力。最终可以讲清楚 Tool 抽象、Mock LLM Provider、AgentRun 状态机和 SSE token streaming 的设计取舍。

三层能力目标

FastAPI 基础能力

掌握 FastAPI() 应用入口、path/query/body 参数、HTTPException、自动 OpenAPI 文档，以及 APIRouter 路由拆分。能从 /api/v1/health 和 Task CRUD 开始，写出结构清晰的接口。

掌握 Pydantic 请求和响应模型，理解它与 Go struct binding 的对应关系：字段声明、默认值、可空字段、校验错误和文档生成都通过 schema 统一表达。

掌握 pytest 与 TestClient，能够覆盖正常场景、404、422、边界输入和基础回归测试，让每次重构都有安全网。

Python 服务端工程能力

从单文件脚本演进为标准后端结构：api/routes 处理 HTTP，schemas 管输入输出，services 管业务编排，repositories 管数据访问，models 和 db 管持久化。

理解配置、日志、异常边界和数据库 session 管理。API 层不直接访问数据库，service 层不关心 HTTP 细节，repository 层不写业务规则。

理解 async/await 更适合 I/O 密集型场景，例如 LLM 调用、token streaming 和 SSE 事件输出；它不是 Go goroutine 的直接替代，而是 Python 生态下的协作式异步模型。

AI Agent 后端能力

把普通 CRUD 后端扩展为 Agent Backend：用 Conversation 表示上下文容器，用 Message 表示 user / assistant / tool 消息，用 Tool 表示可执行能力，用 AgentRun 表示一次 Agent 执行生命周期。

先实现 Mock LLM Provider，再接真实 LLM。这样可以先掌握 provider 抽象、消息编排、工具调用和错误处理，不被 SDK 细节干扰。

用 SSE 处理服务端到客户端的单向事件流：run_started、token、tool_called、tool_result、run_succeeded。它比 WebSocket 更轻量，更适合第一版 token streaming。

项目演进路径

Hello Script→ Health API→ Task CRUD→ DB-backed Service→ Conversation / Message→ Tool + Mock LLM→ AgentRun→ SSE Events

为什么这样演进

这条路径让每一步都建立在上一步之上。Health API 验证服务启动；Task CRUD 验证 FastAPI 基础；DB-backed Service 验证工程分层；Conversation / Message 验证 Agent 上下文；Tool + Mock LLM 验证 Agent 编排；AgentRun 和 SSE Events 验证长任务与流式输出。

每一步都可展示

每周都形成可运行、可测试、可讲述的小版本。这样即使只完成前两周，也能展示 FastAPI 服务端工程能力；完成后两周后，则能进一步展示 AI Agent 后端抽象能力和流式接口设计能力。

最终架构图

Client
浏览器、curl、测试用例或未来前端页面。调用 REST API，接收 JSON 响应；在 Agent 场景下连接 SSE 事件流。
api/routes
HTTP 协议层。定义 Health、Tasks、Conversations、Tools、Agent 路由，负责 request / response、状态码、异常映射和调用 service。
schemas
Pydantic 输入输出模型。负责请求体验证、响应结构、字段类型、OpenAPI 文档和 422 参数错误。
services
业务逻辑和业务编排。TaskService 处理任务规则；ConversationService 处理会话消息；AgentService 编排 provider、tool、run 和 event。
repositories -> models -> db
数据访问与持久化。repositories 封装查询，models 定义表结构，db 提供 engine、session factory、测试数据库隔离和迁移基础。
llm provider
LLM Provider 抽象。第一版使用 Mock LLM Provider，根据 messages 返回 assistant message 或 token generator；后续可替换真实模型 SDK。
tool service -> builtin tools
ToolService 负责工具注册、查找、执行和错误包装。builtin tools 第一版包含 get_current_time、calculator、summarize_text。
core
基础设施层。包含 config、logging、exceptions、responses 和常量，确保横切能力不散落在业务代码里。

核心数据模型

Task

Task
  - id: string
  - title: string
  - description: string | null
  - completed: bool
  - created_at: datetime
  - updated_at: datetime

Task 是第一周到第二周的基础领域对象，用来练习 CRUD、schema、service、repository、数据库持久化和测试数据库隔离。

Conversation

Conversation
  - id: string
  - title: string
  - created_at: datetime
  - updated_at: datetime

Conversation 是 Agent 上下文容器。它把多轮消息聚合在一起，让 AgentService 可以读取历史消息并生成下一轮 assistant 响应。

Message

Message
  - id: string
  - conversation_id: string
  - role: user | assistant | tool
  - content: string
  - created_at: datetime

Message 是 Agent 后端最核心的上下文单位。role 区分用户输入、模型输出和工具结果，content 保存实际文本。

Tool

Tool
  - name: string
  - description: string
  - input_schema: dict

Tool 表示 Agent 可以调用的能力。第一版内置 get_current_time、calculator、summarize_text 三个 mock tool，用于学习工具抽象、schema 描述和执行错误处理。

AgentRun

AgentRun
  - id: string
  - conversation_id: string
  - status: pending | running | succeeded | failed
  - input_message_id: string
  - output_message_id: string | null
  - error: string | null
  - created_at: datetime
  - updated_at: datetime

AgentRun 表示一次 Agent 执行生命周期。它让长任务可以被查询和订阅，也让失败信息有稳定落点。第一版不做 cancel / retry，先把状态流转讲清楚。

Go ↔ FastAPI 概念对照

Go 服务端概念FastAPI / Python 对应迁移理解
Gin/Hertz RouterAPIRouter都负责路由组织。FastAPI 可以按模块拆分 router，再由 app 统一 include，天然生成 OpenAPI。
struct bindingPydanticGo struct 常用于绑定和校验；FastAPI 通过 Pydantic model 统一表达 request、response、校验和文档。
handlerroute functionhandler 处理 HTTP；FastAPI route function 也处理协议层，但依赖、参数和 body 可以从函数签名推导。
service layerservices业务逻辑层。把业务规则从 HTTP 和数据库细节中抽离，便于测试和复用。
daorepositories数据访问层。封装查询、创建、更新和删除，不决定业务语义。
gorm.DBSQLAlchemy Session都是数据库访问入口。FastAPI 常通过 Depends 注入 session，并在测试中替换成隔离数据库。
goroutineasyncio task都能处理并发任务，但模型不同。goroutine 是 Go runtime 管理的轻量线程，asyncio task 是事件循环上的协作式任务。
streaming responseStreamingResponse / SSE都可用于渐进式输出。Agent token streaming 第一版使用 StreamingResponse 输出 text/event-stream，更容易调试和测试。

面试讲述模板

30 秒版本

我做了一个渐进式 FastAPI Agent Backend Demo。项目从 Task CRUD 开始，先掌握 FastAPI 路由、Pydantic 校验和测试；然后重构为 API、service、repository、model 分层，并接入数据库；最后演进成 Agent 后端，支持 conversation、message、tool、agent run 和 SSE 流式事件。这个项目帮助我把 Go 服务端经验迁移到 Python/FastAPI，也为后续学习 AI Agent 框架打基础。

2 分钟版本

这个项目的设计思路是渐进式演进，而不是一开始套复杂模板。第一阶段，我用 Task CRUD 学 FastAPI 的基础，包括 APIRouter、Pydantic request/response model、HTTPException 和 TestClient。第二阶段，我把项目重构成 API、service、repository、model 分层，引入 SQLite 和配置管理，让 API 层只处理 HTTP，service 层处理业务，repository 层处理数据访问。第三阶段，我加入 Conversation 和 Message，把普通后端模型扩展成 Agent 上下文模型；再设计 Tool abstraction 和 MockLLMProvider，让 AgentService 编排模型调用和工具调用。最后，我用 AgentRun 和 SSE 事件流解决 Agent 后端常见的长任务状态查询和流式输出问题。

这个项目最大的价值是建立了 Go 到 Python/FastAPI 的迁移模型：Go 里常见的 handler/service/dao 分层，在 FastAPI 里可以映射为 routes/services/repositories；Go struct binding 可以映射到 Pydantic；context 和依赖传递可以通过 Depends 和显式参数管理；Python async/await 则更适合 I/O 密集型的 LLM 调用和流式响应。

深挖问题

为什么 FastAPI？ 因为类型注解、Pydantic 校验、OpenAPI 文档、依赖注入和 async I/O 都适合快速构建 Agent API。

为什么 service/repository？ 因为 API 层直接访问数据库会让 Agent 编排、工具调用和状态机变得难维护，分层后测试边界更清楚。

为什么 AgentRun？ 因为 Agent 请求可能涉及 LLM、Tool、外部 API 和多步执行，需要 pending / running / succeeded / failed 描述生命周期。

为什么 SSE？ 因为 token 和状态事件是服务端到客户端的单向推送，SSE 比 WebSocket 更简单，也更容易调试。

为什么不 LangChain / LangGraph first？ 因为先理解 conversation、message、tool、provider、run、event stream 的底层边界，再接高层框架会更清楚它解决了什么问题。
